\section{Coleta de lixo}
\label{sec:gc}

Em Java você aloca e o \termo{garbage collector}{Coletor de lixo (GC):
componente da JVM que descobre quais objetos não são mais alcançáveis e
recupera a memória deles.} recupera. A escolha do coletor é uma troca
entre três coisas: \emph{throughput} (aqui, no sentido de GC:
fração do tempo de CPU gasta no seu código, e não em coleta), latência (duração das pausas) e memória. O guia de GC da Oracle
para o JDK~25 (\citetitle{doc:gc-collectors}) descreve os coletores da
HotSpot assim:

\small
\begin{longtable}{@{}p{1.8cm} p{3.2cm} p{7.2cm}@{}}
\toprule
Coletor & Opção & Segundo a documentação \\
\midrule \endhead
Serial & \texttt{-XX:+UseSerialGC} & Uma thread faz todo o trabalho de
  GC; indicado para dados pequenos (até cerca de 100~MB) ou uma CPU \\
Parallel & \texttt{-XX:+UseParallelGC} & Como o Serial, mas com várias
  threads; para quando throughput máximo importa e pausas de um segundo
  ou mais são aceitáveis \\
G1 & \texttt{-XX:+UseG1GC} & Majoritariamente concorrente; busca cumprir
  uma meta de pausa com alta probabilidade mantendo bom throughput. É o
  padrão (\citetitle{doc:jep248}, JDK~9) \\
ZGC & \texttt{-XX:+UseZGC} & Baixa latência, pausas independentes do
  tamanho do heap; o guia fala em pausas máximas abaixo de um
  milissegundo, ao custo de algum throughput \\
\bottomrule
\end{longtable}
\normalsize

\paragraph{A evolução do ZGC.}
O ZGC ficou pronto para produção no \citetitle{doc:jep377} (JDK~15).
O \citetitle{doc:jep439} (JDK~21) acrescentou o modo geracional, o
\citetitle{doc:jep474} (JDK~23) o tornou padrão e o
\citetitle{doc:jep490} (JDK~24) removeu o modo não geracional. Em JDK~25,
\texttt{-XX:+UseZGC} é sempre o ZGC geracional; quem ainda passa
\texttt{ZGenerational} recebe aviso de opção obsoleta.

\paragraph{Shenandoah.}
O \citetitle{doc:jep379} (JDK~15) tornou o Shenandoah um coletor de
produção no OpenJDK; a página do projeto (\citetitle{doc:shenandoah}) o
descreve como um coletor de pausas ultrabaixas que faz mais trabalho
concorrente com o programa. Ele não aparece no guia de GC da Oracle
citado acima: confirme se a distribuição de JDK que você usa o inclui
antes de planejar com ele.

\paragraph{Como ZGC e Shenandoah encurtam as pausas?}
Como o ZGC e o Shenandoah reduzem as pausas \termo{stop-the-world}{Pausa
em que todas as threads do programa ficam paradas enquanto o GC
trabalha.} em comparação com os coletores geracionais tradicionais? O
guia de GC do Java SE~21 descreve o G1 como \enquote{a generational,
incremental, parallel, mostly concurrent, stop-the-world, and evacuating
garbage collector} e diz que ele não é um coletor de tempo real
(\citetitle{doc:gctuning-se21}). A
\termo{evacuation}{Evacuação: copiar os objetos vivos de uma região para
outra e liberar a região de origem inteira.} é a parte que o G1 não faz
junto com o programa: \enquote{it does not do concurrent evacuation}
(\citetitle{doc:jep189}). O ZGC e o Shenandoah movem objetos com as
threads Java rodando, e cada um resolve de um jeito o problema de um
objeto mudar de endereço enquanto o programa o usa.
\begin{itemize}
\item \emph{ZGC.} O \citetitle{doc:jep333} (JDK~11, experimental) baseia
  o desenho em \termo{load barriers}{Barreiras de leitura: um trecho de
  código que a JVM executa quando o programa carrega uma referência do
  heap.} combinadas com \termo{colored pointers}{Ponteiros coloridos:
  referências que guardam, em bits do próprio ponteiro, metadados usados
  pelo GC.}, e limita as fases stop-the-world à varredura de raízes; por
  isso, segundo o JEP, as pausas não crescem com o tamanho do heap nem com
  o volume de objetos vivos. A meta era não passar de 10~ms. O
  \citetitle{doc:jep439} (JDK~21) acrescenta \termo{store
  barriers}{Barreiras de escrita: um trecho de código que a JVM executa
  quando o programa grava uma referência no heap.} no modo
  geracional, põe a meta abaixo de 1~ms e diz que as pausas do ZGC são
  medidas em microssegundos, enquanto as do G1 vão de milissegundos a
  segundos.
\item \emph{Shenandoah.} O \citetitle{doc:jep189} (JDK~12, experimental)
  acrescenta \enquote{an indirection pointer to every Java object}, que
  permite às threads do GC compactar o heap com as threads Java rodando;
  o JEP~333 chama esse recurso do Shenandoah de \emph{Brooks pointers}.
  Segundo o JEP~189, as pausas não dependem do tamanho do heap: são as
  mesmas com 200~MB ou 200~GB. No JDK~13, o
  \citetitle{doc:jdk-8221766} trocou as barreiras antigas: antes, toda
  leitura de um objeto passava por uma barreira de leitura; as novas agem
  quando a referência é carregada, não em cada uso
  (\citetitle{artigo:kennke-lrb-2019}).
\end{itemize}
O preço, segundo o guia do Java SE~21, aparece no throughput: o ZGC tem
pausas máximas abaixo de um milissegundo \enquote{at the cost of some
throughput}.

\paragraph{A decisão que isso muda.}
O guia da Oracle recomenda começar sem escolher nada: deixe a JVM
escolher, ajuste o tamanho do heap e só então troque de coletor, se o
requisito não for atendido. Na prática:
\begin{itemize}
\item API com requisito de latência (p99) apertado: compare G1 e ZGC
  medindo o p99 no teste de carga da Parte~I, não a média.
\item Job batch que só precisa terminar rápido: Parallel é candidato.
\item Container pequeno, com pouca memória e uma CPU: Serial é o que o
  guia indica para esse perfil.
\end{itemize}
Antes de trocar de GC, confira se o problema não é alocação demais: o
autoboxing da seção~\ref{sec:autoboxing} é um jeito comum de criar
objetos sem perceber. O JFR (seção~\ref{sec:ferramentas}) mostra pausas
e alocação por método.
